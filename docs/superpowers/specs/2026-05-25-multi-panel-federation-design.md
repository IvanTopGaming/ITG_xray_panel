# Multi-Panel Federation Design

**Date:** 2026-05-25
**Status:** Approved
**Replaces:** Node system (Node model, node_sync, groups, global_limit_bytes)

## Overview

Transform the current master-pushes-to-dumb-nodes architecture into a federation of independent panel instances. Each panel is a full ITG Xray Panel deployment. A master panel discovers, displays, and manages inbounds/users on its direct child panels. Child panels can also be masters of their own children (tree hierarchy, each level sees only direct children).

## Requirements

### Core

1. **Same codebase** — child panels are ITG Xray Panel instances.
2. **Tree hierarchy** — each panel can be both child and parent; sees only direct children.
3. **Full replacement** of old Node system (groups, global_limit_bytes, NodeClientTraffic, master_disabled removed).
4. **Scope:** master manages only inbounds + users on children (not outbounds/routing/settings).

### Binding

5. Child generates one-time link token -> admin enters token + URL on master -> auto-handshake establishes bidirectional auth.
6. Child sees it is linked but cannot unlink itself.
7. Unlink = clean break (master stops polling, child data untouched).

### Data Model

8. Client data lives ONLY on the panel that owns the inbound.
9. Master reads child data via API, caches in Redis.
10. Master polls children every 10 seconds.
11. Expected scale: 3-5 child panels per master.

### Sync & Conflicts

12. Pull model — master polls children via `GET /api/federation/snapshot`.
13. Bidirectional: child creates user/inbound -> master sees on next poll; master creates -> proxied to child API.
14. Conflict resolution: master always wins.
15. If child is offline when master tries to write -> error to user ("Panel {name} is offline").

### UI

16. Dashboard: all inbounds from all panels in one list, filter by panel on the right side.
17. Nodes page becomes Panels page — panel cards with status/management.
18. Child panel shows "Linked to: {master}" in its Panels page, no unlink button.
19. Offline panels: show last cached data with "Offline" badge, editing blocked.
20. Inbound tags distinguished by panel name prefix on master: "DE-1 / vless-tcp".

### Subscriptions & Traffic

21. Each panel serves its own subscription links.
22. Each panel tracks its own traffic and enforces its own limits independently.
23. Statistics page shows only local data.
24. Backup is per-panel only (master backs up link config, not child data).

### Bot & Billing

25. Bot can run on any level (each panel can have its own bot).
26. TariffItem gets `panel_id` column — two-step selection in UI: choose panel, then inbound.
27. Bot always talks to its own panel's backend; master proxies provisioning to children.

## Federation API

### Authentication

New decorator `federation_token_required` in `app/utils.py`. Checks `X-Federation-Token` header against `federation_config.federation_token`. Constant-time comparison via `hmac.compare_digest`.

New decorator `admin_or_federation_token_required` — accepts either admin JWT or federation token. Used on inbound/user CRUD endpoints.

Federation tokens are `secrets.token_urlsafe(32)` (256-bit entropy).

### Endpoints on child panel

#### Binding

| Method | Path | Auth | Description |
|---|---|---|---|
| `POST` | `/api/federation/link-token` | `token_required` (admin) | Generates one-time link_token, stores in federation_config. 409 if already linked. |
| `POST` | `/api/federation/handshake` | Validates link_token from body | Master calls with `{link_token, master_url, master_name}`. Child validates link_token, generates federation_token, stores master_url + master_name + federation_token, marks link_token_used=True. Returns `{federation_token, name, panel_version, inbound_count}`. |

#### Reading (polling)

| Method | Path | Auth | Description |
|---|---|---|---|
| `GET` | `/api/federation/snapshot` | `federation_token_required` | Returns all inbounds + clients in one response. |

Snapshot response format:

```json
{
  "panel_name": "DE-1",
  "status": "ok",
  "timestamp": 1748188800000,
  "inbounds": [
    {
      "tag": "vless-tcp",
      "port": 443,
      "protocol": "vless",
      "label": "VLESS TCP",
      "stream_settings": {},
      "up": 1073741824,
      "down": 5368709120,
      "clients": [
        {
          "id": "uuid-here",
          "email": "user@example",
          "enable": true,
          "up": 524288000,
          "down": 2147483648,
          "limit_bytes": 10737418240,
          "expiry_time": 1750000000000,
          "reset_day": 1,
          "flow": "xtls-rprx-vision",
          "last_seen": 1748188700000,
          "device_count": 2,
          "tariff_id": null,
          "telegram_id": 123456
        }
      ]
    }
  ]
}
```

#### Provisioning

| Method | Path | Auth | Description |
|---|---|---|---|
| `POST` | `/api/federation/provision` | `federation_token_required` | Creates or extends Client by (telegram_id, inbound_tag). Same logic as local `apply_tariff_for_user` but for a single TariffItem. |

#### Writing (proxied by master to existing endpoints)

| Operation | Child endpoint | Auth |
|---|---|---|
| Create inbound | `POST /api/inbounds` | `admin_or_federation_token_required` |
| Update inbound | `PUT /api/inbounds/<tag>` | `admin_or_federation_token_required` |
| Delete inbound | `DELETE /api/inbounds/<tag>` | `admin_or_federation_token_required` |
| Create user | `POST /api/inbounds/<tag>/users` | `admin_or_federation_token_required` |
| Update user | `PUT /api/inbounds/<tag>/users` | `admin_or_federation_token_required` |
| Delete user | `DELETE /api/inbounds/<tag>/users` | `admin_or_federation_token_required` |

### Endpoints on master

| Method | Path | Auth | Description |
|---|---|---|---|
| `GET` | `/api/panels` | `token_required` | List linked panels (tokens masked) |
| `POST` | `/api/panels` | `token_required` | Link new panel: `{name, url, link_token}` -> triggers handshake |
| `PUT` | `/api/panels/<id>` | `token_required` | Update name/enable |
| `DELETE` | `/api/panels/<id>` | `token_required` | Unlink (clean break) |
| `POST` | `/api/panels/<id>/test` | `token_required` | Test connection |

### Handshake flow

```
1. Child admin: Panels page -> "Generate Link Token" -> copies token
2. Master admin: Panels page -> "Add Panel" -> enters name, URL, token
3. Master backend:
   a. POST {child_url}/api/federation/handshake
      body: {link_token, master_url, master_name}
   b. Child validates link_token
   c. Child generates federation_token = secrets.token_urlsafe(32)
   d. Child stores master_url, master_name, federation_token; marks link_token_used=True
   e. Child returns {federation_token, name, panel_version, inbound_count}
   f. Master stores LinkedPanel with federation_token
4. Master starts polling GET /api/federation/snapshot every 10s
   using X-Federation-Token header with the federation_token
```

## Polling & Caching

### Scheduler job: `poll_linked_panels` (10s interval)

For each enabled LinkedPanel (parallel via gevent):

1. `GET {panel.url}/api/federation/snapshot` with `X-Federation-Token` header, timeout 5s.
2. On success: store response in Redis key `panel:{id}:snapshot` (TTL 60s), update panel status to 'online'.
3. On failure: set panel status to 'offline', store error. Cache NOT deleted (stale data better than nothing; TTL handles eventual cleanup).

### Redis keys

- `panel:{id}:snapshot` — full JSON snapshot, TTL 60s
- `panel:{id}:status` — 'online'/'offline', TTL 120s

### Cache invalidation on write

After master successfully proxies a write to a child panel:

1. Immediately re-fetch `GET /api/federation/snapshot` from that panel.
2. Update Redis cache.
3. Frontend sees fresh data on its next 3s poll cycle.

### Aggregated inbounds API

`GET /api/inbounds` on master is extended:

```
GET /api/inbounds              — all panels (default, backward-compatible)
GET /api/inbounds?panel=local  — only local inbounds
GET /api/inbounds?panel=3      — specific child panel by id
```

Each inbound in the response gets two new fields:
- `panel_id: number | null` — null = local
- `panel_name: string` — "Master" or child panel name

Local inbounds read from DB (as today). Child inbounds read from Redis cache. Merged into one list.

## Proxy Layer

New service: `app/services/panel_proxy.py`

### FederationClient

HTTP client for communicating with a child panel:

- `__init__(url, federation_token)` — stores connection params
- `snapshot()` — GET /api/federation/snapshot
- `create_inbound(payload)` — POST /api/inbounds
- `update_inbound(tag, payload)` — PUT /api/inbounds/{tag}
- `delete_inbound(tag)` — DELETE /api/inbounds/{tag}
- `create_user(tag, user_data)` — POST /api/inbounds/{tag}/users
- `update_user(tag, user_data)` — PUT /api/inbounds/{tag}/users
- `delete_user(tag, email)` — DELETE /api/inbounds/{tag}/users
- `provision(telegram_id, inbound_tag, params)` — POST /api/federation/provision

All methods authenticate via `X-Federation-Token` header.

### Proxy functions

```python
def proxy_create_user(panel_id, inbound_tag, user_data):
    panel = LinkedPanel.query.get(panel_id)
    if panel.status == 'offline':
        raise ValueError(f"Panel '{panel.name}' is offline")
    client = FederationClient(panel.url, panel.federation_token)
    result = client.create_user(inbound_tag, user_data)
    _refresh_panel_cache(panel)
    return result
```

Analogous functions for update_user, delete_user, create_inbound, update_inbound, delete_inbound, provision.

### Routing in existing endpoints

Inbound/user CRUD endpoints on master check for `panel_id` in request:
- `panel_id` absent or null -> local operation (unchanged)
- `panel_id` = number -> route through panel_proxy

## Bot & Billing Adaptation

### Provisioning routing

`services/provisioning.py` -> `apply_tariff_for_user` extended:

For each TariffItem:
- `panel_id is None` -> local create/extend (unchanged)
- `panel_id is not None` -> `panel_proxy.proxy_provision(panel_id, inbound_tag, telegram_id, params)`

The child panel's `POST /api/federation/provision` endpoint runs the same provisioning logic locally: find existing Client by (telegram_id, inbound_tag) and extend, or create new.

### Offline during payment

If child panel is offline during `apply_payment`:
- Proxy raises error, payment stays `pending`
- `poll_pending_payments` (30s) retries when panel comes back
- Existing retry mechanism covers this case without changes.

### Bot events

Master publishes `payment_succeeded` / `access_granted` to Redis `bot:events` after successful proxy call. Child panel is unaware of master's bot.

### Auto-renewal

`auto_renew_free_users`: if TariffItem references a child panel -> proxy provision call. On offline -> skip until next iteration (15 min), log warning.

### Expiry/traffic notifications

For child panel inbounds: read `expiry_time`, `up`, `down`, `limit_bytes` from Redis cache (snapshot data). Notifications sent by master (it owns the bot).

## Security

### Token isolation

- `federation_token` — long-lived, generated by child during handshake, stored on both sides. Used for snapshot reads and proxied writes.
- `link_token` — one-time, generated by child admin, consumed during handshake. Never used after linking.
- Federation endpoints do not accept admin JWT and vice versa.

### Federation token access scope

Allowed:
- `GET /api/federation/snapshot`
- `POST /api/federation/provision`
- Inbound/user CRUD via `admin_or_federation_token_required`

Denied:
- `/api/login`, `/api/backup`, `/api/restore`
- SystemSettings, outbounds, routing
- Other federation endpoints (cannot regenerate link_token or modify federation_config)

### Rate limiting

Federation endpoints excluded from Flask-Limiter (10s polling would hit limits). Access controlled by token validation instead.

## Edge Cases

| Scenario | Behavior |
|---|---|
| Child offline during write | Error 503: "Panel {name} is offline" |
| Child offline during poll | Cache remains (stale), status -> 'offline', last_error populated |
| Cache expired (TTL 60s) and panel offline | Dashboard shows empty list for that panel + "Offline" badge |
| Master deleted inbound referenced by TariffItem | Same as today — tariff becomes unpurchasable |
| Child deleted inbound referenced by master's TariffItem | Next poll shows inbound gone. TariffItem with missing inbound blocks purchase |
| Double handshake attempt | link_token_used=True -> 409 Conflict. Must generate new token |
| Master unlinked but child still has federation_token | Harmless — master stops polling, token is unused dead state. Child can regenerate link_token to re-link. |
| Simultaneous edit by master and child | Master wins: its write proxies to child and overwrites |
| Panel is both child and parent | Works: federation_config (parent link) and linked_panel (children) are independent tables |
| Payment while child offline | Payment stays pending, poll_pending_payments retries at 30s intervals |
| Auto-renewal while child offline | Skipped until next 15-min iteration, warning logged |
